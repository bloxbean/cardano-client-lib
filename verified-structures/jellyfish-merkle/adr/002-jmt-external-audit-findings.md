
# JMT Adversarial Audit Findings — Pre-Remediation Snapshot

These findings describe commits `f040b5a4` / `5e3752b2` before ADR-002 implementation. Line
numbers, behavior, and fix directions below are historical. The current remediation and residual

## CRITICAL

### Replay of a committed version (supported crash-recovery path) marks the version's own live nodes stale, corrupting the tree and causing data loss on prune
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/JellyfishMerkleTree.java:1018* — verdict: **confirmed**

validateCommitVersion (JellyfishMerkleTree.java:1084-1096) explicitly allows re-committing an already-committed version for crash recovery, and tests rely on it (JmtLifecycleHardeningTest.java:57-66). But the commit path is not replay-idempotent: findChildVersion (JellyfishMerkleTree.java:1014-1025, called from insertAtInternal:714) looks up children via cache.getNode(NodeKey.of(childPath, parentVersion)) where parentVersion == the version v being committed. TreeCache.getNode's storage fallback (TreeCache.java:190) then calls store.getNode(v, path), a floor lookup that RESOLVES THE VERSION-v NODES WRITTEN BY THE FIRST COMMIT of v. The replayed transaction treats those post-state nodes as the nodes being replaced: insertAtLeaf/insertAtInternal call cache.deleteNode on NodeKey(path, v), which is not in the staged nodeCache, so TreeCache.deleteNode Case 2 (TreeCache.java:246) adds the LIVE version-v NodeKey to staleNodeIndexCache. The commit then writes both putNode(K) and markStale(K, staleSince=v) for the same live key K. The genesis case is even simpler: TreeCache.initializeRootNodeKey(0) returns NodeKey(EMPTY,0) (TreeCache.java:137-142) and the storage fallback at version 0 finds the committed genesis root itself, so replaying version 0 of a single-key tree stale-marks its own root leaf. Consequences: (a) on InMemoryJmtStore and RdbmsJmtStore, whose getNode(version,path) honors stale markers (InMemoryJmtStore.java:62-64, RdbmsJmtStore.java:110-130), all reads/proofs at version >= v for the affected paths immediately return empty — getProof returns a non-inclusion proof for a key that exists while get() still returns the value; (b) on every store, pruneUpTo(>=v) physically deletes the live nodes (InMemoryJmtStore.java:181-201), permanently destroying the version-v tree; (c) replaying an OLDER committed version (also allowed — any version with an existing rootHash passes the check) stale-marks nodes that newer versions still share, poisoning reads of the latest state too. The divergent-replay root-hash guard does not help because identical replay produces an identical root. TreeCache even has an unused baseVersion field (TreeCache.java:100,116) suggesting the visibility clamp was intended but never wired in. Root cause: unlike Diem, internal nodes do not record child versions, and the floor-lookup substitute uses ceiling v instead of v-1, so replay sees its own post-state.

**Failure scenario:** State: tree.put(0, {alice:100, bob:2}); tree.put(1, {alice:1b}) committed (InMemoryJmtStore). Application crashes after commit 1 but before recording its checkpoint, and on restart replays tree.put(1, {alice:1b}) — the documented supported recovery flow; validateCommitVersion accepts it and the root-hash divergence guard passes (identical root). During replay, findChildVersion(alicePath, cache, 1) floor-resolves the leaf NodeKey(alicePath, 1) written by the first commit; insertAtLeaf marks that exact live key stale (staleSince=1) and rewrites the identical node. Afterwards store.getNode(1, alicePath) sees the floor candidate as stale and returns empty: tree.getProof("alice", 1) returns a NON-INCLUSION proof for an existing key while tree.get("alice", 1) returns "1b" (inconsistent), and store.pruneUpTo(1) physically deletes the live leaf so alice's tree entry is unrecoverable at every version. Genesis variant: put(0, {alice:100}); put(0, {alice:100}) replay stale-marks the root leaf itself — getProof reports an EMPTY TREE at version 0 and pruneUpTo(0) deletes the entire tree. On RocksDbJmtStore (getNode ignores stale markers) the corruption is latent until pruneUpTo runs, then identical permanent loss.

**Fix direction:** Make replay idempotent by clamping every batch-time storage lookup to the pre-state: TreeCache's storage fallback (and findChildVersion) must query store.getNode(min(requestedVersion, nextVersion-1), path), with no storage visibility at all for nextVersion==0 (genesis) — the staged tier already serves current-version nodes. Alternatively adopt Diem's design and record child versions in JmtInternalNode so child lookups are exact against the v-1 root. Additionally, add a cheap commit-time invariant in toBatch()/commitBatchToStore: throw if any NodeKey appears in both batch.nodes() and batch.staleIndices() — this turns any residual self-stale bug into a loud failure instead of silent corruption. Add the two PoC tests as regressions (plus a RocksDB variant that replays then prunes), and either restrict validateCommitVersion to replaying only the LATEST version or document that older-version replay is forbidden.

### Crash-recovery replay marks live nodes stale; subsequent prune silently corrupts the tree
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/JellyfishMerkleTree.java:1014* — verdict: **confirmed**

validateCommitVersion (JellyfishMerkleTree.java:1084-1096) explicitly supports replaying an already-committed version for crash recovery, and tests assert this works (JmtLifecycleHardeningTest.rejectsNewHistoricalVersionButAllowsExistingReplay). But during a replay of version V, findChildVersion (JellyfishMerkleTree.java:1014-1025) probes the store at parentVersion==V first and finds the nodes ALREADY COMMITTED at V by the original commit. insertAtLeaf/insertAtInternal then call cache.deleteNode on those NodeKeys; since they are not in the batch-local nodeCache, TreeCache.deleteNode (TreeCache.java:245-252) adds them to staleNodeIndexCache. The commit therefore writes stale markers (staleSince=V) that point at the LIVE version-V nodes themselves (which are simultaneously re-put with identical content). All three stores accept these markers idempotently. A later pruneUpTo(>=V) — the routine GC operation the stale index exists for — physically deletes the live nodes (InMemoryJmtStore.pruneUpTo:181-201, RocksDbJmtStore.pruneUpTo:783-820, RdbmsJmtStore.pruneStaleNodes:300-329). The same self-stale occurs at the root for a version-0 replay (initializeRootNodeKey returns NodeKey(EMPTY,0) which matches the committed genesis root). No test covers replay+prune; staleNodesUpTo also reports live nodes after any replay, even before pruning.

**Failure scenario:** 1) tree.put(0, {alice:100, bob:200}); 2) tree.put(1, {alice:150}); 3) process crashes after store commit but before app-level ack; on restart the app replays tree.put(1, {alice:150}) — succeeds idempotently (same root, divergence guard passes) but writes a stale marker for the live leaf NodeKey(alicePath, 1); 4) routine store.pruneUpTo(1) deletes that live leaf. Result: getProof("alice", 1) now returns Optional.of(nonInclusionEmpty) for a key that exists (and the proof fails verification), the committed root hash references a node that no longer exists, while tree.get("alice") still returns 150 from the value store — silent divergence between authenticated and unauthenticated reads, and permanent corruption of the latest state.

**Fix direction:** During commit, drop any stale index whose NodeKey is also present in the batch's node set (TreeCache.toBatch or commitBatchToStore can subtract batch.nodes().keySet() from staleIndices). Alternatively, make replay a true no-op: if validateCommitVersion detects rootHash(version) already exists, verify the recomputed root matches and skip the store commit entirely. Add a regression test: replay committed version, then pruneUpTo, then assert proofs still verify.


## MEDIUM

### Replay tests assert only the latest pointer — identical older-version replay silently corrupts latest-value reads in InMemoryJmtStore
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/store/InMemoryJmtStore.java:319* — verdict: **confirmed**

The suite deliberately tests 'crash-recovery replay of an already-committed older version' but every such test asserts only that the latest ROOT POINTER does not regress, never that the latest VALUE of a key updated after the replayed version survives: RdbmsJmtTruncateIdempotentTest.replayingOlderVersionDoesNotRegressLatestPointer (lines 122-138) uses disjoint keys per version; RocksDbJmtPruneTruncateTest.divergentReplayRejectedAndLatestPointerMonotonic (lines 127-151) replays v1 whose key never changes afterwards; JmtLifecycleHardeningTest.rejectsNewHistoricalVersionButAllowsExistingReplay (lines 57-66) likewise. This blind spot hides a real bug: InMemoryJmtStore's commit apply() does values.put(key, val) unconditionally (InMemoryJmtStore.java:317-322), so replaying an identical older version clobbers the latest-values map with the old value while latestRoot() stays at the newer version. RocksDB (getValue -> seekValue(keyHash, -1L), versioned floor read, RocksDbJmtStore.java:746-757) and RDBMS (ORDER BY version DESC LIMIT 1, RdbmsJmtStore.java:183-188) are immune, so the in-memory reference — the ground truth used by the cross-backend comparison tests — silently diverges from both persistent backends.

**Failure scenario:** put(1, {alice=100}); put(2, {alice=200}); then crash-recovery replay put(1, {alice=100}) (accepted by design — identical root). tree.get("alice") now returns "100" while store.latestRoot() is version 2 whose committed tree contains alice=200. Any application doing latest reads after a recovery replay serves stale state contradicting the current root commitment; no existing test fails.

**Fix direction:** Strengthen all three replay tests to update a key at a later version and assert its latest value after replaying the older version (and run the same scenario through the cross-backend comparison test). Fix InMemoryJmtStore.apply() to only update the latest-values map when the batch version is >= the greatest committed version (or derive getValue() from valuesByKey).

### No golden root-hash vectors: the entire proof/root suite is self-referential, so a silent commitment-preimage change would pass every test
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/commitment/ClassicJmtCommitmentScheme.java:58* — verdict: **confirmed**

Every JMT test derives the expected root from the same code that computes it (tree.put(...).rootHash()) and verifies proofs against that root with the same CommitmentScheme instance. No test pins a root hash, leaf commitment, internal commitment, or wire-proof encoding to a hard-coded constant (grep over jellyfish-merkle*/src/test confirms no pinned hex root constants). The sibling MPF module has MpfGoldenVectorsTest; the JMT modules have nothing equivalent. The scheme is explicitly advertised as Diem-compatible and roots are persisted durably by RocksDB/RDBMS backends.

**Failure scenario:** A refactor flips the bitmap byte order in ClassicJmtCommitmentScheme.commitBranch (line 58), changes TAG_LEAF/TAG_INTERNAL, or alters JmtEncoding field order. The entire suite still passes because generation and verification move together. After release, every persisted root in existing RocksDB/RDBMS databases fails to match on replay/verification (or external verifiers built against the documented format reject all proofs), with no test ever having flagged the break.

**Fix direction:** Add a JmtGoldenVectorsTest pinning root hashes for fixed key/value sets (empty, 1 key, N keys), leaf/internal commitment outputs for fixed inputs, and at least one exact wire-proof encoding. If Diem/Aptos compatibility is a real claim, cross-check one vector against the Rust reference.

### Duplicate logical keys in one put() batch yield a nondeterministic committed root (byte[]-keyed Map with identity semantics)
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/JellyfishMerkleTree.java:134* — verdict: **confirmed**

put(long, Map<byte[], byte[]>) uses raw byte[] as map keys. byte[] has identity equals/hashCode, so a caller-supplied HashMap can (and typically will) contain two entries whose key arrays are distinct instances with identical content — the map cannot deduplicate them. The loop at JellyfishMerkleTree.java:147-156 applies both entries; the tree handles the second insert of the same keyHash mechanically correctly (staged leaf is removed via deleteNode Case 1 and rewritten), so last-processed wins for both the tree leaf and the value store. But for a HashMap the processing order is identity-hashCode (memory-address) order, which is unspecified and varies between JVM runs. The committed root hash and stored value therefore depend on nondeterministic iteration order. In the stated target domain (Cardano blockchain state commitment) any nondeterminism in root computation is a consensus hazard: two replicas applying the byte-identical logical batch can commit different roots. Distinct keys are safe — I verified (and the rootIsOrderIndependent property test confirms) that the final tree is order-independent for distinct keys; only duplicate-content keys are affected.

**Failure scenario:** Map<byte[],byte[]> updates = new HashMap<>(); updates.put("k".getBytes(), "v1".getBytes()); updates.put("k".getBytes(), "v2".getBytes()); // second call does NOT replace the first — two entries. tree.put(0, updates) commits root(H(v1)) on some runs and root(H(v2)) on others depending on identity-hash iteration order; two replicas of the same application can permanently diverge on the version-0 root hash, and neither gets an error.

**Fix direction:** Change the put() input to a type with value semantics — e.g., List<Map.Entry<byte[],byte[]>> with documented last-wins order, a Map<ByteArrayWrapper, byte[]>, or pre-hash to SortedMap keyed by keyHash — or detect duplicate keyHashes inside the loop (a HashSet of wrapped keyHash) and throw IllegalArgumentException. At minimum document that duplicate-content keys produce unspecified results and that callers in consensus contexts must deduplicate.

### floorNode/ceilingNode return wrong nodes: raw byte order (length-grouped NodeKey encoding) used for logical path floor/ceiling, and stale markers ignored
*verified-structures/jellyfish-merkle-rocksdb/src/main/java/com/bloxbean/cardano/vds/jmt/rocksdb/RocksDbJmtStore.java:704* — verdict: **confirmed**

NodeKey.toBytes() is [0x4E, pathLenVarInt, packedPath, versionBE8] (NodeKey.java:21-32), and its own javadoc explicitly warns: 'range-based stores must not rely on raw byte order to implement logical floor/ceiling over paths' because byte order groups by path length first. RocksDbJmtStore.floorNode (L704-722) and ceilingNode (L724-743) do exactly that: seekForPrev/seek over the byte-ordered nodes CF, then linearly walk applying the logical predicate (comparePath + version), returning the FIRST match in byte order, which is not the logical floor/ceiling. They also never consult the stale CF, while the JmtStore SPI (JmtStore.java:44-58) says implementations 'should honour stale markers when determining visibility' and InMemoryJmtStore does both correctly (TreeMap ordered by NodeKey.compareTo, isStale checks at InMemoryJmtStore.java:75-123). Additionally getNode(version,path) (L667-689) lacks the stale-visibility check InMemory applies (InMemoryJmtStore.java:62); this is currently unreachable via JellyfishMerkleTree because the core is insert/update-only (every markStale has a same-path replacement), but it is a behavioral divergence at the SPI level. floorNode/ceilingNode have no callers in the tree core today, so this is latent, but it is public SPI shipped to users and diverges across backends (InMemory vs RocksDB vs RDBMS).

**Failure scenario:** Tree contains nodes at paths [1,5] and [2] (any committed version v). floorNode(v, path=[2,0]): byte order sorts [2] (len-1, bytes 4E 01 20 ...) BEFORE [1,5] (len-2, bytes 4E 02 15 ...), so seekForPrev from [2,0] (4E 02 20) lands on [1,5] and returns it; the true logical floor is [2] (InMemoryJmtStore returns [2]). ceilingNode(v, path=[1,6]): seek lands past the only len-2 key and returns empty; the true logical ceiling is [2] (InMemory returns it). Any future range/non-inclusion-proof feature built on these SPI methods produces wrong answers on RocksDB while passing tests on the in-memory store.

**Fix direction:** Either implement floorNode/ceilingNode with a logical-order traversal (e.g., iterate candidate path lengths, or change the on-disk node-key encoding to a non-length-prefixed, order-preserving form) plus stale-marker filtering, or remove/`UnsupportedOperationException` these SPI methods on the RocksDB backend until needed. Pre-release, tightening the SPI (and adding a cross-backend property test: InMemory vs RocksDB floor/ceiling equivalence) is the cleanest fix. Also add the stale check to getNode(version,path) or document that the store relies on the core's insert-only invariant.

### AGGRESSIVE value-prune policy silently deletes the current (live) value of keys not rewritten since the prune horizon
*verified-structures/jellyfish-merkle-rocksdb/src/main/java/com/bloxbean/cardano/vds/jmt/rocksdb/RocksDbJmtStore.java:446* — verdict: **confirmed**

pruneValues (L405-462) deletes every value row with version <= horizon; only the SAFE policy retains a sentinel (the newest row <= horizon, L446-448, skipped in applyValueDeletions L470). Under AGGRESSIVE, the newest row <= horizon is deleted even when it is the key's CURRENT value (no newer row exists). The tree nodes for that key remain live (node pruning is driven solely by stale markers, L802-829), so the Merkle root still commits to the key's valueHash while the value payload is gone. README.md:50-51 describes AGGRESSIVE only as 'removes all such value history' with no warning that it destroys live state; ValuePrunePolicy (L82) has no javadoc.

**Failure scenario:** put version 1 = {alice: 100}; put versions 2..10 touching only other keys; store opened with Options.builder().prunePolicy(AGGRESSIVE); pruneUpTo(10). Alice's only value row (keyHash, v1) has version <= 10 and is deleted. Afterwards store.getValue(aliceHash) and getValueAt(aliceHash, 10) return empty, and tree.getProof("alice", 10) returns an INCLUSION proof (leaf still present in the tree) whose value() is null — the committed state (root includes alice's valueHash) silently disagrees with the value store.

**Fix direction:** Make AGGRESSIVE keep the newest entry per key when no newer entry exists above the horizon (i.e., differ from SAFE only by dropping superseded/tombstone sentinels), or reject AGGRESSIVE prune when it would delete a key's head row. At minimum, add explicit javadoc/README warnings that AGGRESSIVE is only safe when every live key has been rewritten after the horizon (benchmark-style workloads).

### truncateAfter trusts rollback-index completeness that the store never enforces: enabling the index after prior commits (or a disable/re-enable cycle) makes rollback silently serve rolled-back values as current state
*verified-structures/jellyfish-merkle-rocksdb/src/main/java/com/bloxbean/cardano/vds/jmt/rocksdb/RocksDbJmtStore.java:842* — verdict: **confirmed**

nodes_by_ver/values_by_ver rows are written only while enableRollbackIndex is true (putNode/putValue guard on cfNodesByVersion/cfValuesByVersion != null, ~L1057-1097; Builder default is false). truncateAfter (L842-967) deletes future nodes/values exclusively by scanning those index CFs (L906-951). Nothing records since which version the index has been complete, and reopening an indexed DB with enableRollbackIndex(false) silently stops maintaining it while still writing nodes/values. README.md:22-23 warns 'Enable this when the database is first created; it does not backfill old commits', but the store does not enforce the invariant, and violation produces no error — only silently wrong reads, because getValue() resolves the maximum-version row (seekValue, L397-413).

**Failure scenario:** Open store with Options.defaults() (index off); commit versions 1..10 (key K written at v7); close. Reopen with enableRollbackIndex(true); commit v11; call truncateAfter(5). Roots 6..11 are deleted and latestRoot() correctly reports v5, but K's v7 value row and the v6..v10 nodes have no index rows and survive. store.getValue(K) now returns the v7 value — data from a rolled-back version served as current state with no error. Same corruption occurs if the index is enabled at creation, later reopened disabled for a while, then re-enabled and truncated.

**Fix direction:** Persist an 'index-complete-since version' watermark in the roots CF: set it at the first indexed commit, clear/raise it whenever the store runs unindexed, and make truncateAfter throw when versionExclusive < watermark (or when any commits predate index coverage). Alternatively refuse enableRollbackIndex(true) on a non-empty DB whose index CFs are missing/empty.

### No prune watermark: truncateAfter below an already-pruned horizon silently leaves the surviving tree missing nodes
*verified-structures/jellyfish-merkle-rocksdb/src/main/java/com/bloxbean/cardano/vds/jmt/rocksdb/RocksDbJmtStore.java:802* — verdict: **confirmed**

pruneUpTo(h) (L802-839) physically deletes every node whose stale marker has staleSince <= h. A node staled at version s belongs to the live tree of all versions in [nodeVersion, s-1]; pruning to h therefore destroys parts of every tree version below h. truncateAfter(v) (L842) performs no check that v >= the highest pruned horizon — no watermark of prune progress is persisted anywhere — so rolling back below the prune horizon resets the latest pointer to a version whose node set is incomplete. Neither README nor javadoc documents this precondition.

**Failure scenario:** Commit versions 1..1000 (rollback index enabled), pruneUpTo(1000), then truncateAfter(900) (e.g., an over-deep reorg or operator error). Nodes staled during versions 901..1000 — which are interior/leaf nodes of version 900's tree — were already deleted by the prune. truncateAfter succeeds, latestRoot() reports v900, but getProof(key, 900) traversals hit missing children (wrong non-inclusion results or empty lookups), and the next tree.put(901,...) builds new state on top of an incomplete base, permanently corrupting the tree, all without any error at truncate time.

**Fix direction:** Persist a prune watermark (highest versionInclusive passed to a completed pruneUpTo) in the roots CF and make truncateAfter throw IllegalStateException when versionExclusive < watermark. This mirrors Diem/Aptos pruner min-readable-version bookkeeping and turns silent corruption into a loud precondition failure.

### H2Dialect infers MERGE key columns from table-name substrings; legal table prefixes break all commits
*verified-structures/rdbms-core/src/main/java/com/bloxbean/cardano/vds/rdbms/dialect/H2Dialect.java:66* — verdict: **confirmed**

H2Dialect.insertOrIgnoreSql (H2Dialect.java:57-85) picks MERGE KEY(...) columns by substring-matching the resolved table name: contains("jmt_nodes") -> (namespace, node_path, version); contains("mpt_nodes") -> (namespace, node_hash); contains("values") -> (namespace, key_hash, version); otherwise all inserted columns. Table names are prefixed as <tablePrefix>_<base> (TableNameResolver.java:41-48), and TableNameResolver.java:26-32 accepts any prefix matching [a-zA-Z_][a-zA-Z0-9_]*, including prefixes that themselves contain "values", "jmt_nodes" or "mpt_nodes". Such a prefix misclassifies OTHER tables: e.g. prefix "values_a" makes the stale table "values_a_jmt_stale" match the "values" branch, generating MERGE INTO values_a_jmt_stale (namespace, stale_since, node_path, node_version) KEY(namespace, key_hash, version) — key_hash/version are not columns of jmt_stale, so H2 rejects the statement and RdbmsJmtStore.commit() (RdbmsJmtStore.java:524-535) rolls back. Prefix "jmt_nodes_v2" similarly breaks every value write (KEY(node_path) against the values table). The jmt_stale table only works today by coincidence via the default all-columns branch. This is also a layering violation: the generic rdbms-core dialect hardcodes JMT/MPT schema knowledge.

**Failure scenario:** DbConfig with dialect=H2 and tablePrefix="values_a" (accepted by TableNameResolver). First tree.put(1, {k: v1}) succeeds (no stale markers). Second tree.put(2, {k: v2}) supersedes the v1 leaf, so the batch contains markStale entries; commit() builds MERGE INTO values_a_jmt_stale ... KEY(namespace, key_hash, version); H2 throws Column "KEY_HASH" not found; the transaction rolls back and every subsequent update commit fails — the store is permanently unusable for that configuration.

**Fix direction:** Change SqlDialect.insertOrIgnoreSql to take the key columns explicitly (breaking change is acceptable pre-release), e.g. insertOrIgnoreSql(table, columns, placeholders, keyColumns), and have RdbmsJmtStore pass the PK per table. Alternatively make H2 use INSERT ... SELECT ... WHERE NOT EXISTS for true ignore semantics, removing the need to know keys at all.

### getNode(version, path) stale-node visibility diverges across all three backends
*verified-structures/jellyfish-merkle-rocksdb/src/main/java/com/bloxbean/cardano/vds/jmt/rocksdb/RocksDbJmtStore.java:657* — verdict: **confirmed**

RocksDbJmtStore.getNode(long, NibblePath) (RocksDbJmtStore.java:657-679) performs a floor scan over (path, version) but never consults the stale column family. InMemoryJmtStore.getNode (InMemoryJmtStore.java:62-64) returns EMPTY when the newest node <= version is stale, and RdbmsJmtStore.getNode (RdbmsJmtStore.java:113-122, whose comment says 'CRITICAL: Must filter stale nodes like InMemoryJmtStore does') filters stale rows in SQL and therefore FALLS BACK to an older non-stale version at the same path. Three different answers for the identical commit sequence. The current tree core never triggers this because every deleteNode is paired with a same-path replacement, but the stale-marker machinery is exactly the pathway any future deletion/GC support will use.

**Failure scenario:** Via the public SPI: commit v1 putNode((P,1)); commit v5 putNode((P,5)); commit v6 markStale((P,5)) with no replacement. Query store.getNode(6, P): InMemory returns EMPTY, RocksDB returns the logically deleted node (P,5), RDBMS returns (P,1). Any component (GC layer, future delete support, state-sync tooling) relying on stale visibility gets a resurrected/deleted node depending on backend, silently breaking cross-backend root/proof equivalence.

**Fix direction:** Pick one contract and enforce it in all three stores (Diem semantics suggest: floor lookup filters nodes whose staleSince <= queried version). Add a shared JmtStore TCK-style contract test suite run against InMemory, RocksDB and RDBMS covering stale visibility.

### floorNode/ceilingNode return different results on every backend; RocksDB uses raw byte order that contradicts NodeKey's documented ordering
*verified-structures/jellyfish-merkle-rocksdb/src/main/java/com/bloxbean/cardano/vds/jmt/rocksdb/RocksDbJmtStore.java:694* — verdict: **confirmed**

NodeKey.java:28-32 explicitly warns that the byte encoding is length-prefixed (groups by path length first) and that 'range-based stores must not rely on raw byte order to implement logical floor/ceiling over paths'. RocksDbJmtStore.floorNode (694-712) and ceilingNode (715-733) do exactly that: seekForPrev/seek over encoded keys, so nodes at deeper (longer) paths that are logically smaller/adjacent are invisible or skipped. RdbmsJmtStore.floorNode (177-180) just delegates to exact-path getNode, and RdbmsJmtStore inherits the JmtStore.ceilingNode default (JmtStore.java:53-58) that always returns Optional.empty() — while its Javadoc falsely claims it 'delegates to floorNode'. Only InMemoryJmtStore implements logical nibble-order floor/ceiling with stale filtering. Neither method has a production caller today, so this is latent, but any consumer (range iteration, non-inclusion machinery, state sync) will silently diverge per backend. Additionally none of the RocksDB variants apply stale filtering.

**Failure scenario:** Store a single node at path [4,7] at version 1 on all backends, then call floorNode(1, [5]) (logical floor is [4,7] since 4<5): InMemory returns [4,7]; RocksDB returns EMPTY (len-2 group sorts after len-1 in byte order so seekForPrev never reaches it); RDBMS returns EMPTY (exact path only). With nodes at [5,2] and [6], ceilingNode(2, [5]): InMemory returns [5,2] (correct); RocksDB returns [6]; RDBMS returns EMPTY.

**Fix direction:** Either remove floorNode/ceilingNode from the SPI until there is a caller (preferred pre-release, since no production code uses them), or specify logical nibble ordering + stale filtering in the contract, fix RocksDB (needs a length-aware scan or an order-preserving key encoding) and RDBMS (real ORDER BY floor/ceiling query), fix the default's Javadoc, and add cross-backend contract tests.

### pruneUpTo prunes value history on RocksDB/RDBMS but not InMemory, breaking cross-backend equivalence of tree.get(key, version) and prune counts
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/store/InMemoryJmtStore.java:181* — verdict: **confirmed**

The JmtStore.pruneUpTo contract (JmtStore.java:89-92) only mentions deleting stale NODES. InMemoryJmtStore.pruneUpTo (181-201) does exactly that and returns nodes-only counts, leaving all value history intact. RocksDbJmtStore.pruneUpTo (792-829) additionally calls pruneValues (405-462) deleting all value versions <= target except the newest per key (SAFE) or all (AGGRESSIVE), and returns nodesPruned+valuesPruned. Pre-release, tightening the SPI (moving floor/ceiling into an optional capability interface) is also reasonable.

### DbConfig.Builder reuse after build() closes the pool out from under the built config; double build shares ownership
*verified-structures/rdbms-core/src/main/java/com/bloxbean/cardano/vds/rdbms/common/DbConfig.java:110* — verdict: **confirmed**

closeOwnedDataSourceIfAny (DbConfig.java:110-118) closes the builder-owned pool whenever dataSource(...)/jdbcUrl(...)/simpleJdbcUrl(...) is called again — but the builder cannot know the pool already escaped via a prior build() (DbConfig.java:218-226 copies the reference and the ownsDataSource flag without transferring ownership). Reconfiguring the builder after build() therefore closes the live HikariDataSource inside the previously built DbConfig, and every RdbmsJmtStore using it starts throwing. Calling build() twice similarly yields two DbConfigs that both believe they own the same pool, so closing one kills the other.

**Failure scenario:** DbConfig.Builder b = DbConfig.builder(); b.jdbcUrl(url1, u, p); DbConfig c1 = b.build(); RdbmsJmtStore s1 = new RdbmsJmtStore(c1); b.jdbcUrl(url2, u, p); // closes c1's pool. s1.latestRoot() now throws RuntimeException caused by SQLException "HikariDataSource ... has been closed" — the store dies mid-application without c1.close() ever being called.

**Fix direction:** Transfer ownership at build(): after constructing the DbConfig, set the builder's ownsDataSource=false (and optionally null the reference) so later builder calls cannot close an escaped pool and a second build() cannot double-own it. Better still, defer pool creation to build() (see next finding), which removes the entire overwrite-close problem.

### Builder.jdbcUrl starts the Hikari pool before dialect detection; failure or abandonment leaks a live pool
*verified-structures/rdbms-core/src/main/java/com/bloxbean/cardano/vds/rdbms/common/DbConfig.java:174* — verdict: **confirmed**

Builder.jdbcUrl (DbConfig.java:163-181) constructs new HikariDataSource(hikariConfig) at line 174 — HikariDataSource's config constructor starts the pool eagerly (opens a connection via fail-fast) — and only afterwards calls detectDialect(jdbcUrl) at line 178, which throws IllegalArgumentException for any URL other than jdbc:postgresql/h2/sqlite (lines 197-210). If the URL points at a reachable database of another vendor (driver on classpath), the pool starts successfully, then the IAE propagates and the caller discards the builder, leaking a running pool (minimumIdle=2 live connections plus Hikari housekeeping threads, no close path). Independently, any builder on which jdbcUrl() was called but build() never is (validation failure elsewhere, exception between the calls) leaks the eagerly created pool.

**Failure scenario:** DbConfig.builder().jdbcUrl("jdbc:mariadb://dbhost/app", user, pass) with mariadb-java-client on the classpath and the server reachable: HikariDataSource starts, detectDialect throws IllegalArgumentException("Cannot auto-detect dialect..."), caller catches it and moves on — 2 idle connections and the pool's threads remain alive for the JVM lifetime and count against the DB server's connection limit.

**Fix direction:** In jdbcUrl(), run detectDialect BEFORE constructing the pool, and preferably store only the HikariConfig in the builder, constructing the HikariDataSource inside build() (also closing it if build() validation fails). That makes abandoned builders leak nothing and eliminates the overwrite-close machinery.

### Transactional methods never restore autoCommit before returning connections to the pool
*verified-structures/jellyfish-merkle-rdbms/src/main/java/com/bloxbean/cardano/vds/jmt/rdbms/RdbmsJmtStore.java:499* — verdict: **confirmed**

commit() (RdbmsJmtStore.java:498-499), pruneUpTo (lines 281-282) and truncateAfter (lines 357-358) call conn.setAutoCommit(false) and return the connection to the pool without restoring it. HikariCP and the test-only SimpleDataSource are safe (Hikari resets connection state on return; SimpleDataSource really closes), but DbConfig.defaults(dataSource, dialect) (DbConfig.java:49-51) explicitly supports arbitrary caller-supplied DataSources, and common pools such as Tomcat JDBC (without the ConnectionState interceptor) hand the connection to the next borrower with autoCommit still false. Every read method (latestRoot, getNode, getValue, ...) assumes autoCommit and never calls commit()/rollback(), so on such a pool each read after the first write silently opens a transaction that is never ended — on Postgres this accumulates idle-in-transaction sessions, blocks VACUUM, and pins old snapshots.

**Failure scenario:** DbConfig.defaults(tomcatJdbcDataSource /* no ConnectionState interceptor, maxActive=4 */, new PostgresDialect()); after the first tree.put(...), the pooled connection has autoCommit=false; subsequent store.getValue(...) calls run SELECTs inside never-committed transactions; within hours Postgres shows idle-in-transaction backends, xmin horizon pinned, and eventually statement failures once idle_in_transaction_session_timeout kills the sessions mid-borrow.

**Fix direction:** Capture boolean prev = conn.getAutoCommit(); set false; and restore conn.setAutoCommit(prev) in a finally block before the connection leaves try-with-resources, in commit(), pruneUpTo() and truncateAfter().

### RdbmsCommitBatch has no closed/aborted state: close() does not discard staged writes and commit-after-close persists them
*verified-structures/jellyfish-merkle-rdbms/src/main/java/com/bloxbean/cardano/vds/jmt/rdbms/RdbmsJmtStore.java:649* — verdict: **confirmed**

InMemoryJmtStore's batch documents and enforces abort semantics: close() without commit discards staged writes and any later use throws IllegalStateException (InMemoryJmtStore.java:299-303, 338-342). RdbmsCommitBatch.close() (RdbmsJmtStore.java:648-651) only clears the dead 'operations' list — nodeUpdates/valueUpdates/valueDeletions/staleNodes/rootHash survive, there is no closed flag, and commit() can be invoked after close() (or twice) and will happily write everything. The 'operations' list itself (lines 451, 569-572) and the BatchOperation interface (lines 654-657) are dead code that obscures the actual write path.

**Failure scenario:** Caller stages writes on a batch, decides to abort (e.g. validation failed) and calls close(); a later erroneous commit() call (retry loop, framework finally-block) persists the aborted state to the database — on the InMemory backend the same sequence throws IllegalStateException, so code tested against InMemory behaves differently in production against RDBMS.

**Fix direction:** Add a closed flag mirroring InMemoryCommitBatch (throw on any mutation or commit after close/commit), and delete the unused operations list and BatchOperation interface.

### RdbmsCommitBatch has no closed/committed state: commit() after close() silently persists the aborted batch; double commit re-executes
*verified-structures/jellyfish-merkle-rdbms/src/main/java/com/bloxbean/cardano/vds/jmt/rdbms/RdbmsJmtStore.java:648* — verdict: **confirmed**

RdbmsCommitBatch.close() (RdbmsJmtStore.java:648-651) only clears the vestigial 'operations' list; nodeUpdates/valueUpdates/valueDeletions/staleNodes/rootHash survive, and commit() (497-588) has no closed/committed guard. InMemoryJmtStore's batch throws IllegalStateException on any use after close/commit (ensureOpen, InMemoryJmtStore.java:338-342), and RocksCommitBatch throws 'Commit already applied' (RocksDbJmtStore.java:1110-1112) and frees the native WriteBatch on close. The InMemory implementation documents the intended contract: 'close without commit MUST discard staged writes'.

**Failure scenario:** Caller code aborts a batch with close() (e.g., in a finally block after a validation failure) and a later erroneous commit() call on the same object: on RDBMS the aborted nodes/values/root are written to the database (potential divergent state); on InMemory/RocksDB the same code throws IllegalStateException. Double-commit similarly re-executes the SQL on RDBMS but throws elsewhere.

**Fix direction:** Add a closed flag to RdbmsCommitBatch, clear all staged collections in close(), and throw IllegalStateException from commit()/mutators once closed or committed, matching the other two backends.

### JmtStore.getValueAt default silently returns the LATEST value for historical queries
*verified-structures/jellyfish-merkle/src/main/java/com/bloxbean/cardano/vds/jmt/store/JmtStore.java:71* — verdict: **confirmed** · corroborated by 2 auditors
