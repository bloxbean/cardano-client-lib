Contributing to docs

Documentation lives in the www/ directory of the cardano-client-lib repository and is built with Astro and Starlight.

Every page has an Edit page link at the bottom that opens the right file on GitHub — for a typo or a small correction, that is the whole workflow.

Run it locally

Section titled “Run it locally”

Requires Node.js 22.12 or later.

The dev server hot-reloads on save. npm run build produces the static site in dist/ and then runs the link checker; npm run preview serves that build.

Where things live

Section titled “Where things live”

Add a page

Section titled “Add a page”

  1. Create a .md file under src/content/docs/<section>/.

  2. Give it frontmatter — title is required, description is strongly encouraged because it becomes the page summary in search results and in llms.txt:

  3. Add it to the sidebar in astro.config.mjs. Ordering is explicit — the array order is the sidebar order, so file names do not need numeric prefixes.

Do not start the body with an # H1. Starlight renders title as the page heading, so an H1 would appear twice.

Formatting

Section titled “Formatting”

Standard Markdown, plus Starlight’s asides:

Code blocks take a language and an optional title:

Use java, yaml, bash, json, xml or gradle. Anything else falls back to plain text with a build warning.

Links

Section titled “Links”

Use absolute, site-relative paths with a trailing slash:

npm run build fails on a broken internal link or a missing anchor, so a bad link cannot ship.

Things that generate themselves

Section titled “Things that generate themselves”

Do not hand-edit these — regenerate them by changing their source:

OutputSource
/ai/catalog.jsonsettings.gradle, gradle.properties and the Versions list
/llms.txt, /llms-full.txtevery page under src/content/docs/
Versions on the landing pageThe Versions list

The Versions list holds the latest stable and preview versions, so a release edits only that list. If you add a module to settings.gradle, describe it in MODULE_INFO inside scripts/generate-catalog.mjs. Otherwise its catalog entry has an empty description.

Writing guidance

Section titled “Writing guidance”
  • Lead with the reader’s problem, not the API surface. “You need X because Y” beats “X is a class that…”.
  • QuickTx is the recommended path. Unless a page is specifically about TxPlan, TxFlow, TxStream or the composable functions, examples should use QuickTx.
  • Verify code before you publish it. Snippets are copied verbatim by readers and ingested by agents through llms-full.txt. Check signatures against the source tree.
  • Mark preview APIs. TxPlan, TxFlow, TxStream and the verified structures are preview; say so rather than leaving a reader to find out at upgrade time.
  • Say what something is for before how it works. Several of the deeper pages open with architecture; that is right for a reference page and wrong for an entry point.

Submitting

Section titled “Submitting”

Fork, branch, commit, and open a pull request against master. Run npm run build first — it is the same check CI runs, and it catches broken links and missing sidebar entries.
