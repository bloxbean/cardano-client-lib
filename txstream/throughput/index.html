TxStream: Lanes, Batching & Throughput

Experimental

TxStream is experimental, and its APIs and behaviour may change. See known issues before relying on it.

Cardano’s eUTXO model is TxStream’s concurrency model. Two transactions that spend disjoint UTXOs can be in flight simultaneously; two transactions spending the same funds cannot. TxStream expresses that directly:

  • A lane is a funding scope — a funding address or funding reference whose UTXOs at most one in-flight execution may spend at a time.
  • Different lanes run concurrently; the same lane runs serial FIFO. Throughput scales with the number of disjoint funding scopes, not with thread counts.
  • Scheduling keys on the lane’s canonical spending identity, never its display name: two lane labels resolving to the same wallet are one lane wearing two names and share one FIFO. Labels can never be used to sneak two writers onto one wallet.
  • The lane also constrains coin selection: an item’s transaction is mechanically pinned to its lane’s funding scope (violations fail typed TXSTREAM_LANE_SCOPE_VIOLATION), and the lane is declared as the engine’s spending resource — the cross-process safety net if another process ever runs against the same funds. Template items are exempt from the pin: keep each template’s from_ref equal to its lane’s source yourself.

Alias caveat: for funding-ref lanes, identity is the reference string as given (ref:account://sender), caller-asserted canonical. Two different references naming the same wallet — or a ref lane and an address lane over the same wallet — are treated as distinct lanes today; keeping such aliases from running concurrently is your responsibility.

Explicit lanes resolve names through a required LaneIdentityResolver, once per name at first use. An item without a lane fails typed TXSTREAM_LANE_REQUIRED; an unresolvable name fails that item typed TXSTREAM_LANE_UNRESOLVED (it cannot be a startup error — names arrive with items):

Funding-address-derived lanes need no resolver and no per-item lane name — the transaction’s own funding source is the lane, so same-sender items serialize and different senders parallelize for free. An item whose transaction names no funding source fails typed TXSTREAM_LANE_UNDERIVABLE; an item that names a lane must name the derived one or fails TXSTREAM_LANE_MISMATCH (that last rule applies under single(...) too — a lane name is never a silent label):

The default policy is byFundingSource(); the builder call is only needed when making the choice explicit. byFundingAddress() remains a deprecated compatibility alias. Dispatch inherits the engine execution executor unless overridden; give an explicit stream executor at least as many threads as the number of lanes you want concurrently dispatching.

Windows and planners

Section titled “Windows and planners”

By default there is no windowing and the perItem() planner plans every accepted item immediately as its own single-step flow — maximum lane parallelism, true per-item idempotency. Multi-item planning is opt-in via a WindowPolicy plus a planner:

  • WindowPolicy.count(n) — close the window at n items; no timer needed.
  • WindowPolicy.countOrTime(n, maxAge) — n items or the oldest item’s age, whichever first.
  • WindowPolicy.time(maxAge) — age only.

Time-based policies need a scheduler. Set maintenanceExecutor(ScheduledExecutorService), or let the stream inherit the engine’s maintenance executor when it’s a ScheduledExecutorService: the stream owns no threads or timers, so window-age wakeups run on your scheduler (one scheduled wakeup per open window).

The three built-in planners:

  • perItem() (default) — one single-step flow per item. The only planner with per-item exactly-once; sources that redeliver individual items should use this one.
  • perWindow() — one shared flow per lane group in the window; each item rides its own step (its own transaction) of the shared execution. Fewer engine executions, per-item transactions preserved. Flow-level dedup only. perWindow(ChainingMode.PIPELINED) opts into same-lane pipelining: each generated step may fund from every earlier same-lane step’s unspent, matching-address pending outputs. SEQUENTIAL is the default; BATCH is not supported here.
  • batching(options) — merges compatible payment-shaped items within a lane group into one transaction (one flow, one merged step; overflow beyond maxItemsPerTransaction splits into further merged flows). Fewer on-chain transactions and lower total fees; merged members share one fate — the batch confirms or fails together:

What is NOT batchable, and what merging drops. Only pure payments merge: an item carrying a script, mint, staking, governance, metadata, collectFrom, reference inputs, or a contract/datum-bearing output is not payment-shaped and runs unmerged as its own single-item flow (or fails the window typed, with allowNonPaymentSingletons(false)). The merged transaction is a minimal reconstruction from the members’ payment outputs plus the lane’s funding source — per-member transaction context is not carried: extra signers, custom fee payer, change address, and validity windows are dropped. Items needing any of that belong under perItem() or perWindow().

Batching needs a funding-ref lane. A merged plan gets a signer only on a funding-ref lane (ofFundingRef or from_ref). On an address lane the merged transaction has no signer, so the batch fails with No signers found and no funds move.

Dedup warning: perWindow() and batching(...) provide flow-level dedup only, and under batching a re-batched payment is a real second on-chain payment. Read dedup scopes before using either with a redelivering source.

Custom planners implement TxStreamPlanner — plan a closed window into executions, deriving flow and step ids from the context’s StableIdFactory (determinism is an SPI obligation: the same items must produce a byte-identical plan, or redeliveries become TXFLOW_IDEMPOTENCY_CONFLICT failures). Plans are validated before dispatch (TXSTREAM_PLAN_INVALID, TXSTREAM_PLAN_CROSS_LANE); a planner that throws fails only that window’s items (TXSTREAM_PLANNER_FAILED), never the stream.

Partitioned lanes: the fan-out deep-dive

Section titled “Partitioned lanes: the fan-out deep-dive”

Items may use QuickTx extensions registered on the engine (FlowEngine.Builder.extension or FlowRuntime.Builder.extension). An unregistered extension is rejected at submit with TXSTREAM_NON_PORTABLE_ITEM, batching(...) never merges extension items, and perWindow() splits items with conflicting bindings into separate flows on the same lane.

LanePolicy.partitioned(...) is the full UTXO throughput story for a single logical wallet: the funding source is split across N lane addresses, items are assigned by hash(idempotencyKey) % N (stable across restarts), and the N lanes run concurrently — throughput scales with N, not block time.

Pre-fund your lanes in this preview

The built-in bootstrap transaction carries no signer, so bootstrap(true) fails start() with TXSTREAM_BOOTSTRAP_FAILED. Fund the lane addresses yourself and use bootstrap(false).

Items must leave from and from_ref unset, or name exactly their assigned lane address; otherwise they fail TXSTREAM_LANE_SCOPE_VIOLATION. A plan’s signers must be able to sign for whichever lane the hash assigns:

With bootstrap(false) the lanes are assumed pre-funded. Min-ADA per lane and consolidating lanes on shutdown are the caller’s economics — the stream never manages keys.

FUNDS-CRITICAL: the partitioned configuration must be byte-stable across restarts. The funding source, the per-lane seed, the lane count N, and the lane-address list including its order all feed the bootstrap’s idempotency claim — changing any of them mints a new claim, i.e. a new split that re-drains the funding wallet; and the address order additionally defines the partitionIndex → lane mapping, so reordering remaps every item’s lane even with N and the addresses unchanged. A durable partitioned stream persists the bootstrap fingerprint and fails start() typed (TXSTREAM_BOOTSTRAP_CONFIG_DRIFT) on any drift, before submitting a split. A non-durable stream has nowhere to persist the fingerprint and cannot detect drift — it will silently re-split. Run partitioned streams durable unless you are certain the configuration is generated deterministically.

Template items currently require an explicit lane (single or explicit); under byFundingSource()/partitioned(...) they fail typed TXSTREAM_LANE_REQUIRED.

Honest throughput expectations

Section titled “Honest throughput expectations”

What the current built-ins actually deliver:

  • Lanes are real parallelism — N disjoint funding scopes give up to N concurrent in-flight executions (devnet-validated), bounded by maxInFlight.
  • Batching is real transaction reduction — up to maxItemsPerTransaction payments per on-chain transaction (devnet-validated: two payments merged into one transaction).
  • Within one flow, perWindow() is SEQUENTIAL by default: a flow of 50 items confirms its 50 steps one at a time, and a lane running perItem() flows waits for each item’s confirmation before dispatching the next. perWindow(ChainingMode.PIPELINED) with a WindowPolicy submits a window’s steps without waiting for confirmation between them. The lane still runs one execution at a time, so the next window waits for the current one, and windows of one gain nothing. Dedup stays flow-level.

So today’s levers, in order: more lanes (explicit or partitioned), then batching (fewer, larger transactions), then perWindow(PIPELINED) with window sizing. If a lane must exceed roughly one transaction per confirmation interval and batching cannot absorb it, that is the signal to partition further.

Feeding a stream from java.util.concurrent.Flow

Section titled “Feeding a stream from java.util.concurrent.Flow”

For reactive pipelines, TxWorkSource.fromPublisher(...) bridges a Flow.Publisher<TxWorkItem> with real demand-based backpressure: the adapter prefetches a bounded number of items (default 64), requests one more as each accepted item settles, and parks items while the buffer is full or the stream is an ownership standby (PAUSED) — items are never dropped and demand is never unbounded. TxStreamFlowPublisher is the outbound half: an event listener that publishes item results to Flow subscribers.

Subscribers must not block in onNext (Reactive Streams §2.2). Delivery is inline on the stream’s callback thread — the thread that advanced the item’s projection. A subscriber that blocks inside onNext stalls that lane’s further dispatch (other lanes, other subscribers, and the item’s own completion() are unaffected). A merely slow (under-requesting) subscriber is different and safe: its bounded buffer (default 256) overflows and it is terminated with TxStreamSubscriberOverflowException and dropped — it never back-pressures the stream.

Scalability notes

Section titled “Scalability notes”
  • maxInFlight (default 16) caps concurrent executions across all lanes, on top of the one-per-lane rule. Ready lanes are scheduled round-robin, so one lane’s backlog cannot starve the others.
  • Lane maps are unbounded. Resolved lane identities and their FIFO state are retained for the stream’s lifetime. Under byFundingSource() with high-cardinality senders (many thousands of distinct funding addresses through one stream), that map grows without bound — prefer a bounded set of explicit or partitioned lanes for that shape.
  • maxBufferSize (default 1000) bounds accepted-but-undispatched items; submit blocks and trySubmit reports FULL when it is reached. A count-only window larger than the buffer is rejected at build() (it could never fill).
  • One stream instance per lane set: sharing a lane’s funding scope across processes without ownership mode is out of scope until the engine’s cross-process busy-claim path lands; the engine’s spending-resource coordination is the safety net, not a throughput feature.

Backend indexing and qualification

Section titled “Backend indexing and qualification”

Confirmation and UTxO indexing can become visible at different times. Backend-based engines enable TxStream’s between-execution output-visibility check by default. It holds the lane until the preceding transaction’s output zero is queryable, bounded by the stream’s backendVisibility(timeout, pollInterval) budget. A timeout fails new work before engine start with TXSTREAM_BACKEND_NOT_READY; the preceding transaction remains confirmed or uncertain as previously reported.

Custom four-supplier engines must opt in with backendVisibilityChecks(true) and provide historical output lookup. This check does not establish atomic consistency across all provider endpoints or coordinate unrelated spenders. Measure both confirmation and indexing delay with the provider used in deployment.

The soak runner also has its own application submission gate. Report gated and ungated runs separately; a gated throughput result must not be presented as a measurement of the ordinary SDK submission path. Preview qualification should include delayed indexing, unavailable output lookups, and consecutive same-lane payments without that application gate.

Backend visibility retries release the worker and in-flight slot between probes. FlowRuntime supplies the retry scheduler. Direct stream builders inherit the engine’s maintenance executor when it implements ScheduledExecutorService; an explicit stream maintenanceExecutor(...) takes precedence. When neither provides a scheduler, an unsuccessful probe fails before engine start. A plain Executor cannot schedule retries. Plain close() keeps retries active while it drains and cancels remaining timers afterward; abort cancels them immediately. Parked executions retain their buffer permits, so maxBufferSize includes them. The pending hashes are process-local and reset on restart; authoritative FAILED/CANCELLED repair clears the affected item’s hold. A visibility timeout fails every member of the waiting execution. Their IDs remain registered. Because this particular error proves the engine never started, the caller may retry that work under new IDs; this does not apply to RECOVERY_REQUIRED. Custom backend-based engines used by TxStream enable visibility checks by default; custom output services must support historical output lookup or explicitly disable backendVisibilityChecks. Ordinary engine executions do not invoke this stream gate.
