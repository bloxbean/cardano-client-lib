TxFlow Getting Started

TxFlow turns an ordered set of QuickTx transactions into one observable execution. A portable definition is reusable: runtime values, execution identity, backend services, signers, policy, and durability remain application-owned.

This guide uses the portable v1alpha1 contract and FlowEngine. The historical version: "1.0" / flow: document and FlowExecutor APIs are compatibility surfaces, not the recommended starting point for new applications.

Baseline: TxFlow is built and tested on Java 17. FlowEngine accepts caller-owned Executor instances rather than creating threads. A Java 21 application can therefore supply a virtual-thread executor without changing TxFlow code.

Parse and inspect diagnostics

Section titled “Parse and inspect diagnostics”

Use TxFlowCodec for application input. It preserves warnings and structured errors that the TxFlow.fromYaml(...) convenience method cannot expose before throwing.

parse(...) performs bounded YAML/JSON decoding plus portable envelope and graph checks. For a validation-only endpoint, TxFlowValidator.standard().validate(source) exposes the same parser diagnostics without returning a definition. Parameter binding, resource lookup, and server policy belong to the later compilation/preflight phase.

Supply runtime bindings

Section titled “Supply runtime bindings”

Portable parameters are not replaced in the YAML text. The compiler binds values in the parsed transaction tree, preserving native integer and boolean values.

Unknown, missing, incorrectly typed, and out-of-range bindings become compilation diagnostics. The reusable TxFlow definition is not mutated.

FlowEngine needs four small backend interfaces:

  • UtxoSupplier for transaction input lookup;
  • ProtocolParamsSupplier for current protocol parameters;
  • TransactionProcessor for submission; and

Build the engine, preflight, and start

Section titled “Build the engine, preflight, and start”

The application owns the executor and decides its lifecycle. The Java 17 example uses a bounded platform-thread pool:

Preflight compiles a bound, policy-checked, one-transaction TxPlan for each step and produces a deterministic definition fingerprint. start(...) intentionally compiles again: it never assumes a previous preflight result still represents the submitted request.

Without a FlowExecutionStore, idempotency and active-execution tracking are process-local. For restart recovery or multiple application instances, configure the RDBMS store and a separately provisioned maintenance executor. See Durable runtime.

RECOVERY_REQUIRED isn’t a failure. A confirmation timeout ends this way because the transaction may still land. Don’t resubmit under a new execution ID or idempotency key; check the transaction hash first.

On Java 21, the same builder accepts a virtual-thread executor created and closed by the application. TxFlow depends only on Executor and never detects, creates, or shuts down a thread implementation.

The execution pipeline

Section titled “The execution pipeline”

The safe application path is:

  1. TxFlowCodec.parse decodes YAML or JSON and reports structural and graph diagnostics.
  2. FlowBindings supplies run-specific portable scalar values.
  3. TxFlowCompiler—directly or through FlowEngine.preflight—binds values, applies server policy, resolves resource metadata, validates explicit output references, and materializes QuickTx plans.
  4. FlowEngine.start claims execution/idempotency identities, coordinates spending resources, and dispatches work on the caller’s executor.
  5. FlowExecutionHandle exposes ordered events, cooperative cancellation, and the terminal FlowExecutionResult.
