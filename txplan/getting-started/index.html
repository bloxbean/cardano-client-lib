TxPlan: Getting Started

Preview API

TxPlan ships inside the quicktx module — no extra dependency. It is stable enough to build on, but its YAML schema may still change before the stable release.

A Tx written in Java hardcodes the decisions. TxPlan moves them into a YAML document your application loads at run time — so a payout schedule, a treasury operation, or a customer-specific transfer becomes configuration you can review in a pull request rather than code you have to redeploy.

You need: Java 17+, cardano-client-lib, a backend, and a funded test account. If you have not built a transaction with this library yet, do Your first transaction first — this page assumes you know what Tx, from and a signer are.

The plan file

Section titled “The plan file”

To parameterise the file, replace those values with ${...} by hand. Save the result as payment.yaml:

Four parts, and it is worth knowing which is which:

  • variables — the values every ${...} placeholder resolves against.
  • context — settings that apply to the whole plan and map onto QuickTxBuilder: fee_payer, fee_payer_ref, collateral_payer, collateral_payer_ref, signers, required_signers, valid_from_slot, valid_to_slot, additional_signers_count, deposit_payer, deposit_mode. Note these keys are snake_case.
  • transaction — a list of - tx: entries. A plan can carry several entries, each with a different sender. They are merged into one on-chain transaction with one hash.
  • intents — what each transaction actually does. type: payment here; minting, delegation, governance and script intents have their own types.

Load and execute

Section titled “Load and execute”

compose(TxPlan) maps the plan’s context block onto the builder for you — fee_payer becomes the fee payer, valid_to_slot becomes the validity bound. You do not repeat them in Java.

Where runtime values come from

Section titled “Where runtime values come from”

This is the one thing worth getting right early.

Variable expansion happens when the YAML is parsed, against the document’s own variables: block. TxPlan.from(yaml) returns a plan whose transactions are already fully materialised — so calling addVariable(...) on that returned plan does not change them. addVariable populates a plan you are serialising out; it does not inject into a plan you have read in.

To vary values per run, pass them to TxPlanCodec:

Runtime values override the document’s variables:, and an exact ${name} keeps the value’s native type. TxPlanCodec is marked experimental.

For addresses and signing keys that are fixed per environment rather than per run, the signer registry is cleaner than variables: reference them as account://ops and resolve them at compose time with compose(plan, signerRegistry). See Advanced usage.

When TxPlan is the right tool

Section titled “When TxPlan is the right tool”
SituationTxPlan?
One transaction shape, values differ per callYes — one plan file, different variables
Operators need to review transactions before they runYes — the plan is reviewable text
An agent or external system decides what to submitYes — generating config is safer than generating code
Transaction shape is fixed and known at compile timeNo — plain QuickTx is simpler
Several transactions that depend on each other’s outputsNo — that is TxFlow
A continuous stream of transactions over timeNo — that is TxStream

TxPlan describes what to submit. It does not orchestrate ordering, dependencies or retries — that is TxFlow’s job, and TxFlow can execute plans as its steps.
